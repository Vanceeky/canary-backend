Canary Backend

API Reference

The REST contract this backend exposes to the SDK, the web dashboard, the landing/onboarding app, and the mobile app. Every request/response shape, auth rule, and error code your integration needs — nothing here requires reading backend source. As of Phase 15: each project has members directly, invitations bring teammates in — including a one-step register-with-token join straight from the invite — and a superadmin can see every user and project in the system.

Base URL  https://canary-backend-pi.vercel.app Prefix  /api/v1 Format  JSON
How a request gets here
SDK (browser) → POST /events → persist + group → notify (best-effort)
Dashboard / Mobile → session token → GET /errors · /stats · /projects
Project owner → POST /projects/:id/invitations → invitee registers with token (or accepts) → access to that project

Every error, on every endpoint below, uses the identical shape. Build your error handling against error.code — it's stable; the message text may be reworded.

Two independent bearer namespaces. A project API key (from creating a project) and a user session token (from login) both use Authorization: Bearer <token> — but are never interchangeable. Each endpoint below states which one it expects.

Authentication

Register → Login → receive a session token → call authenticated endpoints with it → Logout. No cookies — the same bearer token works identically for a browser app and a native mobile client.

POST /api/v1/auth/register Public

Creates a developer account. Does not log the user in — call /auth/login afterward for a session token.

Request body

FieldTypeReq.Notes
namestringyes1–200 chars
emailstringyesValid email, max 320 chars, lowercased/trimmed server-side
passwordstringyes8–200 chars
invitationTokenstringnoSee register-with-token below

Response 201

JSON
{
  "success": true,
  "user": {
    "id": "usr_...",
    "name": "Ada Lovelace",
    "email": "ada@example.com",
    "role": "USER",
    "createdAt": "2026-08-26T10:30:00.000Z"
  },
  "invitation": { "status": "accepted", "projectId": "proj_..." }
}

role is "USER" unless this email is on the server's SUPERADMIN_EMAILS allowlist — see Admin. Checked here and re-checked on every login; promotion-only, never auto-demoted.

Register with an invite token — one step, not two. Pass invitationToken and the new account is auto-joined to that invitation's project in the same request, no separate authenticated accept call needed. The invitation key only appears in the response when a token was sent, and it never blocks account creation — a bad, expired, or mismatched token still creates the account; only invitation.status reflects what happened ("accepted", "not_found", "expired", or "email_mismatch"). A brand-new invitee can preview what they're joining first with GET /invitations/preview — no account required.

POST /api/v1/auth/login Public

Returns a session token exactly once. A wrong email or wrong password both produce the identical 401 INVALID_CREDENTIALS — deliberate, so the response can't reveal whether an email is registered.

Request body

FieldTypeReq.Notes

Projects

A project represents one monitored app, with exactly one owner and, optionally, directly-attached members (see Project Members). Every endpoint below is scoped to projects the caller owns — a project id belonging to someone else returns 404 PROJECT_NOT_FOUND, never 403. Being a member only grants read access to error data, self-assignment, and error status (see error assignment) — it never transfers rename/delete/key-rotation rights away from the owner.

GET /api/v1/projects Session token

Lists every project the caller can access — ones they own, plus ones they've been invited into and joined as a member. Unpaginated — a developer's accessible-project count is expected to be small.

API Keys

Keys are managed as part of Projects — creation always issues one atomically, so there's no "project with no key" state and no standalone issuance endpoint. The only additional call is rotation.

POST /api/v1/projects/:projectId/api-key/rotate Session token

Issues a new key and immediately invalidates the previous one — no grace period. Any SDK still using the old key fails on its very next event.

Response 200

JSON
{ "success": true, "apiKey": "mnst_bfd181356ecfa17ba525f10d2ae1286..." }

Errors

401 UNAUTHORIZED 401 INVALID_SESSION 404 PROJECT_NOT_FOUND 500 INTERNAL_ERROR
curl example
Shell
curl -s -X POST "$BASE_URL/api/v1/projects/$PROJECT_ID/api-key/rotate" \
  -H "Authorization: Bearer $TOKEN"

Key lifecycle: issued at creation → shown once → used by the SDK on every event → optionally rotated (old key dies instantly, new key shown once) → retired when the project is deleted. There is no way to view a full key after its issuing response.

Event Ingestion

What the SDK actually calls, from end-user browsers. Everything else in this API reads what this endpoint writes.

POST /api/v1/events Project API key

Validates, persists, and groups a captured event into Project → ErrorGroup → ErrorEvent. Grouped by fingerprint = type + message (plus method+url for http events, whose message is often a generic string shared across unrelated endpoints).

Request body — mirrors the SDK's CapturedEvent exactly

Errors

Query what event ingestion produced, and assign error groups to a project member. The web dashboard and the mobile app consume these exact same endpoints — there are no mobile-specific duplicates. Every list uses the same pagination shape: "pagination": { "page": 1, "limit": 20, "total": 27 } — limit defaults to 20 (max 100); invalid values are rejected, never silently clamped. Every endpoint here accepts the project's owner or any of its members — see Project Members.

Notifications

Prepares the backend for mobile push without integrating a real provider yet. There's no dedicated endpoint — this documents the side effect of POST /api/v1/events.

Architecture
SDK→ POST /events→ persist event→ determine trigger→ NotificationService→ devices
Logged, not delivered. No Expo/FCM credentials exist in this project — ConsoleNotificationService logs exactly what would be sent. Swapping in a real provider changes one factory function, nothing else.

Trigger rules — at most one per event

1st NEW_ERROR The event created a brand-new error group.
2nd SERIOUS_ERROR A repeat http occurrence with statusCode ≥ 500.
3rd REACTIVATED_ERROR The group's previous occurrence was over 24h ago.

If more than one applies, only the highest-priority trigger fires. An ordinary repeat of an already-active group triggers nothing.

Payload — deep-links a mobile client to the error

JSON
{
  "type": "NEW_ERROR",
  "projectId": "proj_...",
  "errorGroupId": "grp_...",
  "title": "New Error Detected",
  "message": "500 GET /api/users"
}
manual ASSIGNED_ERROR Fired by PATCH /errors/:id, never by event ingestion — doesn't compete with the three triggers above and can fire alongside one of them on the same group.

Invitations

How someone joins a project. Invitations are per-project — there is no guaranteed email-delivery mechanism in this backend, so an invitation's raw token is always returned directly in the creation response; this backend also attempts to actually email it via SMTP when a Gmail account (or similar) with an App Password is configured, falling back to a logging-only placeholder otherwise. Either way, the token in the API response is the reliable way to deliver an invite, not a fallback. A brand-new person can join in one step by registering with the invite token — no separate accept call needed.

GET /api/v1/projects/:projectId/invitations Session token · owner only

Lists the project's pending invitations.

Response 200

JSON

CORS

Applies to every endpoint — browsers call this API directly, so every route supports CORS the same way, via an explicit allowlist (CORS_ALLOWED_ORIGINS). Never a wildcard.

  • An allowed origin gets Access-Control-Allow-Origin reflected back, plus Access-Control-Allow-Methods (that route's real methods + OPTIONS) and Access-Control-Allow-Headers: Content-Type, Authorization.
  • A disallowed or missing origin gets no CORS headers on either the preflight or the actual response — the browser blocks it client-side.
  • Non-browser callers (curl, server-to-server, the mobile app's HTTP client) are entirely unaffected — CORS is a browser-only mechanism.
  • A custom Authorization header and JSON content type mean every cross-origin POST triggers a real preflight OPTIONS first.
  • No Access-Control-Allow-Credentials is ever sent — this API only uses bearer tokens, never cookies.

Rate limiting

Two endpoints are limited — a simple in-memory fixed-window counter, no Redis or other new infrastructure. Correct for a single-process deployment; a multi-instance deployment would need a shared store.

EndpointLimitKey
POST /auth/login10 / 5 minNormalized email
POST /events100 / 60 secProject id

Exceeding a limit returns 429 RATE_LIMITED with a Retry-After header (seconds until reset) — read it and back off, don't retry in a tight loop.

Known limitations

Documented gaps, not silent ones — nothing below is a bug you'll discover the hard way.

  • Notifications are logged, not delivered — no real push provider is wired up yet.
  • CORS is a single global allowlist, not per-project yet.
  • Rate limiting is in-memory and per-process — not correct for a horizontally-scaled deployment.
  • No pagination on GET /api/v1/projects — fine while project counts stay small.
  • API-key rotation is immediate and unconditional — no grace period, no rollover window.
  • Project deletion is immediate and irreversible — cascades, no undo.
  • No "log out everywhere" — only the exact token given to /auth/logout is invalidated.
  • No password reset flow — needs an email delivery mechanism this backend doesn't have.
  • Error grouping is message-based, not stack-based — a textually different message for "the same bug" forms a separate group.
  • Search is a plain substring match on message — no fuzzy matching, no full-text index.
  • No GET /api/v1/devices — only register/delete exist.
  • os and metadata exist as columns but are always null — reserved, not derived.
  • No cascading unassign when a member is removed from a project while still assigned to one of its error groups — the (now stale) assignment is left in place, not automatically cleared.
  • Invitation uniqueness is application-level, not a DB constraint — Postgres can only express "unique while pending" via a partial index, not expressible in the schema DSL used here.
  • Invitation emails require SMTP configuration to actually deliver — set a Gmail account (or similar) with an App Password to send real email; otherwise it just logs what would be sent. The token in the creation response is always the reliable delivery path either way.
  • Superadmin role is snapshotted into the session token at login — a change to SUPERADMIN_EMAILS only takes effect on that user's next login, not live mid-session.
  • No endpoint to grant/revoke SUPERADMIN — bootstrapped purely via the environment variable, promotion-only.
  • A project's members get access, not co-ownership — members can read error data and manage assignment/status; only the direct owner can rename/delete a project, rotate its key, or invite/remove members.
